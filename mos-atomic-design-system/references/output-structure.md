# Output structure — one root, one entry file, one spec per component

Read this when scaffolding a new system, when writing or regenerating
`README.md`, or when the user asks to migrate a v1 system to v2. It is the full
version of the tree in `SKILL.md`, with the reasoning.

---

## The tree (schemaVersion 2)

```
design-system/
├── README.md                 START HERE — AI + human entry point
├── STATE.json                build state: schemaVersion 2, stages, approvals, inventory, version, themes
├── CHANGELOG.md              one entry per approved stage / publish, semver
├── brief/
│   └── DESIGN-BRIEF.md
├── tokens/
│   ├── tokens.css            CANONICAL — the only file anywhere with raw values
│   ├── tokens.json           generated — W3C DTCG, tiers + modes preserved, aliases as {refs}
│   ├── TOKENS.md             generated — one table per tier: token | light | dark | use for
│   └── figma/                optional — only when export-figma.ts is run
│       ├── README.md
│       └── <collection>.<mode>.json
├── foundations/
│   └── FOUNDATIONS.md        colour, type, space, grid, shape, elevation, motion, a11y
├── components/
│   ├── INDEX.md              generated — every ID: name, level, spec, status, composes, states
│   ├── atoms/A-01-button.md
│   ├── atoms/icons.md        one spec for the whole icon set (icons get I-nn IDs, no per-icon files)
│   ├── molecules/M-01-search-field.md
│   ├── organisms/O-01-site-header.md
│   └── templates/T-01-homepage.md
├── rules/
│   └── RULES.md              promotion ladder, ownership, guardrails, a11y floor, change protocol
└── reference/                human visual review site (static HTML, noindex)
    ├── index.html  foundations.html  atoms.html  icons.html  molecules.html
    ├── organisms.html  templates.html  pages.html  rules.html
    ├── styles.css            the one stylesheet; imports ../tokens/tokens.css; mapped tokens only
    ├── snapshots/            Stage 0 inspiration screenshots (brief links ../reference/snapshots/x.png)
    └── pages/P-01-<slug>.html
```

File names are lowercase kebab slugs with zero-padded IDs. A spec file is
`<ID>-<slug>.md`, and the slug matches the specimen's name.

---

## Why it's shaped like this

**One root.** v1 split a system across `docs/`, `public/` and `src/` to mirror
a site layout. That made sense for a human browsing a site repo and was
awkward for everyone else: an agent had to know three conventions to find the
tokens, and deleting or moving a system meant hunting in three places. One
folder can be found by one glob, copied as a unit, and reasoned about
without knowing the host framework.

**One entry file.** `README.md` is the only file an agent — or a new
developer — needs to open first. It says what the system is, where every other
file is and what it's for, how to consume the tokens, and the handful of rules
that must not be broken. Everything else is reachable from it in one hop.

**One spec per component.** A single `COMPONENT-MAP.md` holding every
component grows into a file nobody can load into context without paying for
the other 40 components. One file per ID means an agent building a site header
reads `O-01-site-header.md` and the specs it `composes:` — nothing else.
Frontmatter (`id`, `level`, `status`, `composes`, `tokens`, `specimen`, and
optionally `implementation` — the path in the product codebase once one
exists) makes each file machine-readable without parsing prose.

**Generated indexes.** `components/INDEX.md`, `tokens/tokens.json`,
`tokens/TOKENS.md` and the file-index section of `README.md` are rebuilt by
`scripts/build-index.ts` from the source files. Hand-maintained indexes drift
the first time someone adds a component in a hurry; generated ones can't.
Each carries a `generated by scripts/<x>.ts — do not hand-edit` header. Edit
the source (a spec file, `tokens.css`) and re-run the script.

**Machine-readable tokens.** `tokens.css` stays canonical because the site
consumes CSS. `tokens.json` (DTCG) exists for everything that isn't a browser —
Figma, native apps, other build tools — and for agents that want to look up a
token's resolved value without evaluating CSS.

**Reference is for humans.** The HTML review site is where approvals happen;
it isn't where an agent should look first. It lives under `reference/` so it
doesn't clutter the docs an agent reads.

## How an AI agent should consume the system

Put this (adapted) in the README's usage section:

1. Open `design-system/README.md`. Read the non-negotiable rules.
2. For tokens: import `design-system/tokens/tokens.css`. Look names up in
   `tokens/TOKENS.md`; use only mapped and responsive (`--text-*`) tokens —
   the README lists the mapped prefixes.
3. For a component: find its ID in `components/INDEX.md`, open that spec, then
   the specs listed in its `composes:`. Copy the Markup section as the starting
   point.
4. Only use components with `status: approved`. `draft` ones may change.
5. Need something that doesn't exist? Don't invent it in the site — propose it
   through the change protocol in `rules/RULES.md`.

---

## README.md — the entry point spec

Template: `assets/docs/README.md`. Keep it under ~150 lines. Sections:

1. **What this is** — brand, version, status, themes, one line on the ladder.
2. **Start here** — the five-step consumption list above.
3. **Consuming the tokens** — the import path. If the site framework can't
   import from outside its source folder, say so and name the sync step (a
   script or build copy) that puts a copy where it can.
4. **Non-negotiable rules** — the canonical list lives in the template
   (`assets/docs/README.md`); don't restate it elsewhere, point at it. Brand
   guardrails from `RULES.md` may be appended, one line each.
5. **File index** — generated by `build-index.ts` between marker comments; one
   line per top-level file with its purpose. `components/` is summarised as
   counts plus a link to `components/INDEX.md` — never one line per spec, or
   the README stops fitting in ~150 lines the moment the system grows.
6. **Inventory** — counts per level as ready / draft / legacy / total
   (generated).

## Component status

| Status | Meaning | Counts as ready? |
| --- | --- | --- |
| `draft` | built, not yet signed off; may change | no |
| `approved` | signed off at a stage gate | yes |
| `legacy` | usable and in production, but built before v2 and never signed off under it (set by a migration) | no — counted separately |
| `deprecated` | retired; spec kept with a pointer to its replacement | no |

`legacy` exists so a migration can carry forty working components across
honestly: they're usable, but nobody has reviewed them against the v2 spec.
Promote each to `approved` when it passes a stage review.

## Versioning and the changelog

`STATE.json` carries `version` as semver. The scaffold starts at `0.0.0` and
Discover leaves it there.

| Event | Bump |
| --- | --- |
| Build stage approved (before 1.0) | minor — `0.1.0` Foundations, `0.2.0` Atoms … `0.5.0` Templates |
| Pages approved | `1.0.0` — published |
| Amending an approved stage | patch |
| Re-approving a stale downstream stage | patch, one per stage |
| New component or token after 1.0 | minor |
| Removing or renaming a token or ID after 1.0 | major |
| Figma export, notes, open decisions | none — goes under `## Unreleased` |

`CHANGELOG.md` gets one entry per bump, listing only what changed — added,
changed, removed, with IDs. Events that don't bump the version (a Figma export
run, a recorded note) go in the `## Unreleased` section at the top and are
folded into the next versioned entry. The course's Figma equivalent is
republishing only changed components; a changelog is the written version of
that, which the course doesn't cover.

## v1 → v2 path mapping

A v1 system has a `STATE.json` without `schemaVersion: 2` (its `version: 1`
field was the schema number). v1 came in two layouts:

| v1 (site repo) | v1 (self-contained) | v2 |
| --- | --- | --- |
| `docs/design-system/STATE.json` | `design-system/docs/STATE.json` | `design-system/STATE.json` |
| `docs/design-system/DESIGN-BRIEF.md` | `design-system/docs/DESIGN-BRIEF.md` | `design-system/brief/DESIGN-BRIEF.md` |
| `docs/design-system/COMPONENT-MAP.md` | `design-system/docs/COMPONENT-MAP.md` | `design-system/components/<level>/<ID>-<slug>.md` + generated `components/INDEX.md` |
| `docs/design-system/RULES.md` | `design-system/docs/RULES.md` | `design-system/rules/RULES.md` |
| `src/styles/tokens.css` | `design-system/reference/tokens.css` | `design-system/tokens/tokens.css` |
| `public/atomic-framework/*.html` | `design-system/reference/*.html` | `design-system/reference/*.html` |
| `public/atomic-framework/<page>.html` (page refs) | `design-system/reference/<page>.html` | `design-system/reference/pages/P-nn-<slug>.html` |
| `public/atomic-framework/styles.css` | `design-system/reference/styles.css` | `design-system/reference/styles.css` |
| — | — | `README.md`, `CHANGELOG.md`, `foundations/FOUNDATIONS.md`, `tokens/tokens.json`, `tokens/TOKENS.md` |

Note the self-contained v1 layout also lives under `design-system/` — detect
the version from `STATE.json`, never from the folder name.

## Legacy systems (hand-built, no STATE.json)

Some brands have an atomic system built before this skill existed, with no
`STATE.json` at all — an existing project's `public/atomic-framework/*.html`, a legacy project's
`reference/brand/atomic-design/stage-*.html` in a sibling repo. Discovery
reports them as `existingAtomicSystem`. Extend them in their own files and
naming: add to the existing pages, keep their markup, class and ID
conventions, and don't scaffold v2 around them unless the user asks to migrate.

- **`ATOMIC-NOTES.md` beside the system** records new work (what, why, date),
  this run's brand source and inspiration map, and how the legacy pages map
  onto the ladder. Map by content, not file name — a legacy project's
  `stage-1-atoms.html` is ladder Stage 2 (Atoms), because its own "stage 1" is
  the brand doc. A small table (legacy file → ladder stage → what it covers) is
  enough.
- **When the system lives in a sibling repo** and the target is a different
  (often empty) site repo, write a short `DESIGN-SYSTEM.md` at the target's
  root saying where the system lives and how to reach it. Without it, the next
  person to open the site repo has no idea a system exists.
- **A sibling repo is a second repo.** Writing there touches a repo the user
  didn't name, so say so and get a yes first; with approvals waived, record it
  in `ATOMIC-NOTES.md` and the run notes instead.
- **The quality floor still applies** — visible `:focus-visible` on every
  interactive element, 44px targets, contrast, and an inspiration map with take
  *and* leave filled. Legacy conventions decide naming and structure, not how
  much accessibility the extension gets.
- **Verify** with `verify-stage.ts --legacy <dir>`, which runs the generic
  checks: noindex, raw values, and a visible `:focus-visible` rule reachable
  from every page that has something focusable (the page's own `<style>` or a
  stylesheet it links).

The mapping table above applies loosely when migrating one — an existing project's layout
matches the v1 site-repo column, minus the `STATE.json` and docs.

## Default: extend v1 in place

Systems built by the old skill (v1 `STATE.json`) stay v1 unless the user asks
to migrate. `init-system.ts` detects a v1 system and leaves it alone
(`--schema 1` scaffolds a missing v1 file, and is only for this case);
`verify-stage.ts` reads the schema version and applies the matching checks.
When extending a v1 system, write new work in its existing layout and
conventions (primitives, opacity text hierarchy, `COMPONENT-MAP.md`). Someone
approved those decisions; silently restructuring them is the same mistake as
silently replacing them.

## Migration procedure (only on request)

Run it on a branch in the target repo. Each step is reviewable, and the order
matters: move first so git keeps each file's history, scaffold second so
nothing is overwritten, fill third.

1. **Inventory.** List every legacy/v1 file and every ID (`A-nn` … `P-nn`)
   with its status. This is the checklist the migration is judged against —
   nothing may be lost.
2. **Move with `git mv`.** Move the existing reference pages into
   `design-system/reference/` (page references into `reference/pages/`) and any
   docs into `brief/` and `rules/`. `git mv` keeps the history attached.
3. **Scaffold the rest:** `init-system.ts --target <repo> --migrate --scaffold`.
   It prints the path mapping and creates the missing v2 folders and files
   alongside what you moved. It moves nothing, never overwrites an existing
   file, works while a legacy `public/atomic-framework/` or v1 system is still
   present, and drops a `.gitkeep` in empty folders so the tree survives a
   commit.
4. **Fill `STATE.json`** (`schemaVersion: 2`): carry over stage statuses,
   approvals, notes and inventory. For a legacy system with no `STATE.json`,
   reconstruct them from the pages and ask the user which stages count as
   approved. Set `"migratedFrom": "legacy"` (see step 7 for what it changes)
   and `version` to reflect approved stages.
5. **Re-tier the tokens** into `tokens/tokens.css` (`token-architecture.md`):
   expand each primitive into a full brand scale with the original value at its
   natural step, add alias roles, map the old names onto mapped tokens. Keep
   the old names in a `/* @deprecated */` block at the end of the mapped tier so
   production doesn't break mid-migration. Where opacity hierarchy can't be
   replaced without visible change, `--brand-<hue>-a<NN>` is the stopgap (see
   "Migration aids" in `token-architecture.md`).
6. **Split the component docs** into one spec file per ID, filling the
   COMPONENT-SPEC sections from the old map or notes, the specimen and its CSS.
   IDs don't change. Components nobody has signed off under v2 get
   `status: legacy`.
7. **Repoint the reference.** `styles.css` imports `../tokens/tokens.css`. Move
   component CSS onto mapped tokens as you go. With `migratedFrom: legacy`, the
   verifier reports leftover raw literals and hexes in `reference/styles.css`
   and inline styles as one warning line with a count instead of a failure per
   literal, so the migration can land before every literal is cleaned up.
   Checks on the token file itself stay strict. A complete ID set that sits out
   of page order (an existing `A-08` kept its number and now precedes `A-07`)
   is also a warning, not a failure; gaps and duplicates still fail.
   Deprecated tokens may point at mapped *or* responsive tokens
   (`--font-size-h1: var(--text-h1-size)`).
8. **Repoint the site** at `design-system/tokens/tokens.css`. If the site
   still serves the reference at its old URL (e.g. `/atomic-framework/`), add a
   small sync script that copies `design-system/reference/` into the site's
   public folder at build time, and name it in the README — the copy is never
   edited by hand. Reference pages that use site-absolute asset paths
   (`/fonts/…`, `/images/…`) only render correctly when served, not over
   `file://`; say that in the README too. Fix any tests that assert old paths.
9. **Generate.** Run `build-index.ts`; write `FOUNDATIONS.md`, `README.md` and
   a `CHANGELOG.md` entry ("Migrated to schema v2 — no component changes").
10. **Verify every stage** (`verify-stage.ts --stage <n>` for each approved
    stage) and compare the reference pages side by side with the originals.
    Visual differences are bugs unless they're the intended contrast fixes.
11. **Remove the old files** only after the user has reviewed the result.

## Script reference

Every user-relevant flag, in one place. `$SKILL` is
the real folder containing the loaded `mos-atomic-design-system/SKILL.md`; run each as
`bun $SKILL/scripts/<script> …`. `--target` defaults to the current directory.

| Script | Flags | Use |
| --- | --- | --- |
| `discover-brand.ts` | `--target <repo>` · `--siblings <dir>` (default: target's parent; override when the active brain lives elsewhere) · `--all` (include archived docs) · `--quiet` · `--json` | Stage 0: find the brand doc and any existing atomic system. Exit 3 = nothing found for this brand |
| `init-system.ts` | `--target <repo>` · `--page <file>[,<file>]` or `--page all` (write stage pages from `assets/shell.html` with the rail and its `aria-current` generated; `--force` regenerates) · `--brand-name "<name>"` · `--themes light,dark` (first = default theme; `dark,light` for a dark-default brand) · `--schema 1` (only to extend an old-skill v1 system) · `--migrate` (print the path mapping, move nothing) · `--migrate --scaffold` (also create the missing v2 tree, never overwriting) · `--siblings <dir>` (passed to discovery) · `--no-discover` (skip the sibling check; tests/offline) · `--force` (overwrite scaffold files; ignored with `--migrate`) · `--json` | Scaffold a new system, or report what exists and stop |
| `verify-stage.ts` | `--target <repo>` with `--stage <n>` or `--all` · `--legacy <dir>` (generic checks on a hand-built system) · `--json` | The mechanical gate before a stage is shown. Exit 1 = failures |
| `export-tokens.ts` | `--target <repo>` · `--json` | `tokens.css` → `tokens.json` (DTCG) + `TOKENS.md`; Stage 1 build beat |
| `build-index.ts` | `--target <repo>` · `--json` | Runs export-tokens, regenerates `components/INDEX.md` and the README index; after every approval |
| `export-figma.ts` | `--target <repo>` · `--json` | Optional: `tokens.json` → `tokens/figma/` |
| `grade-run.ts` | `--run <dir>` · `--eval <id>` | Eval harness only |

Waived approvals (non-interactive mode) are not a flag on any script. It's a
behaviour: when the user explicitly says not to stop for approvals (or an eval
prompt runs non-interactive), skip the gate question, record "approved without
review (waived by user)" in `STATE.json` and the changelog, and present every
gate together at the end — see "Waived approvals" in `stage-specs.md`. Likewise
"where are we" is answered by reading `STATE.json`, not by a `--status` flag.

## The `/* @specimens */` marker in `styles.css`

`init-system.ts` writes `reference/styles.css` as the chrome (from
`assets/styles-base.css`) followed by one comment:
`/* @specimens — everything below is component CSS … */`. It splits the file in
two. Above it is the viewer's chrome, which may hold literals (it styles the
reference site, not the brand). Below it is component and specimen CSS, which
`verify-stage.ts` holds to the strict rule: mapped and responsive tokens only,
no hex, px, rem or ms. Append each stage's CSS below the marker, under its
banner comment. If the marker is missing, the verifier falls back to the first
`/* ---- A-nn …` style banner; with neither, it warns that the strict literal
check couldn't find the component CSS and skips it — so a missing marker hides
literals rather than failing them. Put it back if it gets deleted.
